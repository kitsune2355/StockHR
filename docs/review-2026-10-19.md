# ตรวจระบบสต็อก Uniform — 19 ต.ค. 2569

ตรวจทั้งระบบหลังเชื่อมกับระบบสวัสดิการ (hl-welfare) เสร็จ ว่ายังขาดอะไร หรือมีอะไรเสี่ยง
เรียงตามความสำคัญ แต่ละข้อบอกหลักฐาน (ไฟล์:บรรทัด) และทางแก้สั้น ๆ

ภาพรวม: โค้ดหลักแข็งแรง — SQL ใน backend/ ใช้ prepared statement เกือบทั้งหมด
ทุก action ที่เขียนข้อมูลใน api/ ตรวจ CSRF หน้าเว็บ escape ข้อมูลก่อนแสดง
ทุกการเปลี่ยนยอดสต็อกผ่าน `stock_apply`/`stock_set` ที่ล็อกแถวและลง `tb_stock_movement`
ปัญหาที่หนักอยู่ที่ไฟล์เก่าที่ค้างใน repo, การตั้งค่าเซิร์ฟเวอร์, รหัสผ่าน และงานปฏิบัติการ (สำรองข้อมูล/แจ้งเตือน)

---

## ทำแล้วในรอบนี้ (แก้เล็กที่ปลอดภัย)

| เรื่อง | ทำอะไร |
|---|---|
| `config_ctrl/qr_autologin.php` เข้าระบบเป็นใครก็ได้ด้วย `?u=<username>` ไม่ถามรหัสผ่าน (รวม super_admin) | ปิดผ่านเว็บด้วย `config_ctrl/.htaccess` (ได้ 403) — **ยังไม่ได้ลบไฟล์** ดูข้อ 1 |
| `config_ctrl/checkmember_1.php`, `checkmember_new.php` มี SQL injection | ปิดผ่านเว็บเหมือนกัน |
| โฟลเดอร์ที่ไม่ควรเปิดผ่านเว็บได้ HTTP 200 (`sql/` มีรหัสผ่าน dev + รหัส admin ตั้งต้น, `backend/`, `pages/` ที่หลายไฟล์ไม่มีตัวกันล็อกอิน, `includes/`, `docs/`, `.claude/`, `PHPMailer_v5.0.2/examples` ที่ส่งเมลได้) | ใส่ `.htaccess` ปฏิเสธทั้งโฟลเดอร์ (รองรับ Apache 2.2 และ 2.4) |

ตรวจแล้ว: โฟลเดอร์ข้างบนได้ 403 ส่วน `login.php`, `main.php`, ล็อกอิน (POST `config_ctrl/checkmember.php`), `logout.php`, `sign.php`, `approve.php`, `api/welfare.php`, `assets/` ใช้ได้เหมือนเดิม
`cron/` ยังเปิดไว้เพราะมีทางเรียก `mail_worker.php?key=` ผ่านเว็บ (ข้อ 17)

> `.htaccess` ใช้ได้เมื่อโฮสต์เปิด `AllowOverride` — ต้องตรวจบนเซิร์ฟเวอร์จริงหลัง deploy ว่าได้ 403

## สูง — ควรทำก่อนใช้งานจริง

1. **ลบไฟล์เก่าที่อันตรายออกจาก repo** — `config_ctrl/qr_autologin.php`, `checkmember_1.php`, `checkmember_new.php`
   และไฟล์ที่ไม่มีใครเรียก: `checksession_menu.php`, `DetechGuest*.php`, `DetechAdmin*.php`, `DetechOwnerOnly.php`, `alert.php`, `token_helper.php` (ต้องใช้ PHP 7)
   รอบนี้ปิดผ่านเว็บไว้แล้ว แต่ถ้าโฮสต์ไม่อ่าน `.htaccess` ไฟล์จะกลับมาใช้ได้ทันที → `git rm` ไฟล์เหล่านี้
   (ไฟล์บนดิสก์ที่ไม่อยู่ใน git: `config.inc.php`, `config2.inc.php` มีรหัสฐานข้อมูลเก่าในคอมเมนต์ ลบด้วย)

2. **รหัสผ่านเก็บแบบ `md5(md5(md5()))` ไม่มี salt** — `config_ctrl/checkmember.php:47`, `backend/user.php:76-78`
   → เปลี่ยนเป็น `crypt()` แบบ Blowfish (`$2a$`, ใช้ได้บน PHP 5.2.6) แล้ว rehash ตอนผู้ใช้ล็อกอินครั้งถัดไป

3. **รหัสผ่านตั้งต้นที่ทุกคนรู้** — admin ตั้งต้น `admin`/`admin1234` (`sql/001_create_tb_user.sql:109-116`, README)
   ปุ่มรีเซ็ตรหัสผ่านตั้งเป็น `4123` ทุกคน และโชว์ในข้อความ (`backend/user.php:86`, `:648-652`) ไม่บังคับเปลี่ยน
   → สุ่มรหัสชั่วคราว + ธง `must_change_password` บังคับเปลี่ยนตอนล็อกอิน

4. **ไม่มีการกันเดารหัสผ่าน** — ล็อกอินผิดกี่ครั้งก็ได้ ไม่มีบันทึกครั้งที่ผิด (`config_ctrl/checkmember.php`)
   → ตารางบันทึกการล็อกอินผิด ล็อก ~15 นาทีหลังผิด 5 ครั้งต่อผู้ใช้/IP

5. **ไม่มีระบบสำรองข้อมูล** — ไม่มีสคริปต์ ไม่มี cron ไม่มีเอกสาร (`sql/039` อ้างโฟลเดอร์ `C:\AppServ\backup_stock_hr\` ที่ไม่มีอยู่จริง)
   → `mysqldump` ทุกคืน เก็บย้อนหลัง N วัน + สำรอง `assets/img/company`, `assets/img/product` + เขียนขั้นตอนกู้คืนใน README แล้วซ้อมกู้คืนจริงหนึ่งครั้ง

6. **ขั้นตอน deploy ใน README รันไฟล์ทำลายข้อมูล** — วนรันทุกไฟล์ใน `sql/` ซึ่งรวม `039_reset_transactions.sql` (ลบเอกสาร/ความเคลื่อนไหว/ยอดคงเหลือทั้งหมด)
   และ `074_uniform_catalog.sql:40-41` (ลบชุดของ/สิทธิ์สินค้า) และข้อมูลตัวอย่าง (021, ตัวอย่างใน 075) ไม่มีตารางจำว่ารันไฟล์ไหนไปแล้ว
   → ตาราง `schema_migrations`, ระบุไฟล์ที่ห้ามรันบนเครื่องจริง (039, demo), เขียนขั้นตอนอัปเดตแบบรันเฉพาะไฟล์ใหม่

7. **ไม่บังคับ HTTPS และ cookie ไม่มีธงความปลอดภัย** — ไม่มี `session_set_cookie_params` ที่ใด PHP 5.2 ค่าเริ่มต้นไม่มี HttpOnly/Secure
   ไม่มี redirect ไป HTTPS, HSTS, X-Frame-Options, nosniff
   → `session_set_cookie_params(0, '/', '', $https, true)` ก่อน `session_start` ทุกจุด + redirect/headers ใน `.htaccess` ของเครื่องจริง
   (ระบบสวัสดิการส่งข้อมูลพนักงานมาทาง `api/welfare.php` — ต้องเป็น HTTPS ระหว่างสองเซิร์ฟเวอร์)

## กลาง

8. **API ไม่หมดเวลา และไม่ตรวจว่าผู้ใช้ถูกระงับ** — `api_require_login()` (`api/_bootstrap.php:112-118`) ไม่ดู `sess_last_activity` / `is_active`
   ผู้ใช้ที่ถูกระงับยังเรียก API ได้จน session หมดเอง → ตัวกันเดียวกับหน้าเว็บ: ตรวจเวลาว่าง ต่ออายุ และตรวจ `is_active`/role ซ้ำ

9. **สิทธิ์เมนูกับสิทธิ์ API ไม่ตรงกัน** — หน้าเว็บอ่าน `tb_menu_permission` (`includes/menu.php:224-275`) แต่ API ใช้รายการ role ตายตัว
   ปิดเมนู (เช่น `report_stock`, `report_movement`, `issue_history`) ให้คนทั่วไปแล้ว API ยังตอบ (`api/reports.php:20` ตรวจแค่ล็อกอิน)
   → ผูกแต่ละ action กับคีย์เมนูแล้วเรียก `app_can_access`

10. **ราคาทุนหลุดไปถึงคนที่ไม่ใช่ผู้ดูแล** — `api/reports.php` action stock/low ส่ง `unit_cost` ทุก role (`backend/stock.php:164, 211`)
    และ `api/documents.php` export_lines (`:570-571`) → ตัด `unit_cost`/`amount` สำหรับคนที่ไม่ใช่ admin (แบบเดียวกับ action movement `:87-99`)

11. **ผู้อนุมัติยกเลิก/ทำใบจ่ายของหน่วยงานอื่นได้** — `issue_cancel` ตรวจแค่ role (`backend/issue.php:307`) ต่างจากใบเบิกที่ตรวจ `user_has_department` (`backend/request.php:155, 565`)
    → ใช้การตรวจหน่วยงานเดียวกันกับการทำ/ยกเลิกใบจ่าย

12. **ไม่มีอะไรตรวจว่ายอดคงเหลือตรงกับความเคลื่อนไหว** — ไม่มีรายงานเทียบ `tb_stock_balance` กับผลรวมของ `tb_stock_movement`
    (`sql/040` สร้างยอดตั้งต้นโดยไม่มีแถวความเคลื่อนไหว) การตรวจนับมีแค่ใบปรับยอด ไม่มีใบนับ/ส่วนต่างย้อนหลัง
    → รายงานหรือการ์ดสุขภาพข้อมูล "สินค้าที่ยอดไม่ตรงกับความเคลื่อนไหว" + รายงานส่วนต่างการตรวจนับ

13. **แจ้งเตือนของใกล้หมดไม่ถึงใคร** — มีหน้า `report_low` และตัวเลขแดงในเมนู มีประเภทแจ้งเตือน `stock_low` (`backend/notify.php:41`) แต่ไม่มีโค้ดไหนสร้าง
    → หลังจ่าย/ปรับยอดจนต่ำกว่าขั้นต่ำ (หรือ cron วันละครั้ง) ส่งกระดิ่ง+เมลหาผู้ดูแล

14. **ความเคลื่อนไหวของสต็อกแก้/ลบในฐานข้อมูลได้** — ไม่มี trigger/สิทธิ์ที่บังคับให้เพิ่มได้อย่างเดียว
    → ให้ user ของแอปมีแค่ INSERT/SELECT บน `tb_stock_movement` หรือ trigger กัน UPDATE/DELETE
    (ยกเลิกใบปรับยอดลงเป็น `move_type='adjust'` แยกไม่ออกจากการปรับจริง — เพิ่มค่า `cancel_adjust`)

15. **ระบบสวัสดิการ ↔ สต็อก**
    - ลายเซ็น HMAC ไม่มีตัวกันยิงซ้ำ (nonce) — `sync_master` ที่ถูกยิงซ้ำภายใน 5 นาทีจะทับข้อมูลที่ใหม่กว่า (`backend/welfare_bridge.php:88-106`)
      → เก็บ hash ของลายเซ็น 10 นาทีแล้วปฏิเสธซ้ำ
    - สถานะไหลกลับไประบบสวัสดิการด้วยการดึง (`status`) เท่านั้น และดึงเมื่อ HR กดปุ่ม — คลังยกเลิกใบ WRQ/NRQ แล้วฝั่งสวัสดิการยังไม่รู้จนกว่าจะกด
      → ให้ระบบสวัสดิการดึงสถานะตามรอบเวลา (เช่นทุก 15 นาที) หรือเพิ่ม callback
    - ระบบสวัสดิการยกเลิกใบ (`welfare_cancel`, `backend/welfare_bridge.php:680-727`) คลังไม่ได้แจ้งเตือน → เรียก `notify_event_doc_cancelled`
    - บัญชีระบบ `hl-welfare` (ผู้ขอของทุกใบ WRQ/NRQ) ผู้ดูแลรีเซ็ตรหัส/เปิดใช้งานได้ แล้วจะเซ็นรับแทนได้ทุกใบ → ล็อกบัญชีนี้ใน `user_guard`
    - ใบที่จ่ายบางส่วนยังรายงานเป็น REQUESTED (ไม่มีสถานะ "จ่ายบางส่วน") — ตกลงกับฝั่งสวัสดิการว่าต้องการไหม
    - ข้อมูลบนเครื่อง dev ทุกสินค้าที่เปิดใช้เป็นชุดฟอร์ม (จับคู่ใน `tb_welfare_item_map`) ชุดของพนักงานใหม่ของสต็อกจึงยังเลือกอะไรไม่ได้ — ต้องลงทะเบียนสินค้าที่ไม่ใช่ชุดฟอร์ม (บัตรพนักงาน, เครื่องเขียน) ก่อน
    - หน้าบริษัท/แผนก (`pages/agencies.php`) ยังแก้ชื่อ/บริษัท/สถานะของรายการที่มาจากระบบสวัสดิการได้ แล้ว sync ครั้งถัดไปจะทับ → ติดป้าย "จากระบบสวัสดิการ" และล็อกช่องเหล่านั้น

16. **การเลือกเครื่อง dev/จริงดูจาก Host header** — `config_ctrl/connect.php:21-33` (และ `192.168.*` = dev) ปลอม Host บนเครื่องจริงแล้วจะไปใช้ค่าของ dev
    ลิงก์ในเมล/ลิงก์อนุมัติถ้าไม่ได้ตั้ง `site_url` ก็สร้างจาก Host (`backend/setting.php:88-113`)
    → ตัดสินเครื่องจากพาธ/ค่าฝั่งเซิร์ฟเวอร์ และบังคับตั้ง `site_url` บนเครื่องจริง (ไม่ตั้ง = ไม่ส่งลิงก์)

17. **การจัดการข้อผิดพลาด** — ไม่มี `display_errors`/`log_errors` ที่ใด ขึ้นกับ php.ini ต่อฐานข้อมูลไม่ได้ `die()` เป็นข้อความธรรมดา (API ได้ข้อความแทน JSON และอาจเห็นข้อความ MySQL)
    → `display_errors=0`, `log_errors=1`, `error_log` ใน php.ini/.htaccess + ต่อฐานไม่ได้ใน api/ ตอบ JSON 500
    ตัวส่งเมลทาง `cron/mail_worker.php?key=` ส่งกุญแจทาง URL (ติดใน access log) — ใช้ cron/schtasks แทนแล้วปิดทางเว็บ

18. **PHPMailer 5.0.2 เก่ามาก มีช่องโหว่ที่รู้กันแล้ว** — รอบนี้ปิดโฟลเดอร์ผ่านเว็บแล้ว แต่ควรลบ `examples/`, `test/`, `docs/` และวางแผนอัปเกรด

19. **token ของลิงก์อนุมัติ/เซ็นรับไม่ได้สุ่มแบบเข้ารหัส** — `sha1(uniqid(mt_rand(), true))` (`backend/approve_link.php:87`, `backend/sign_link.php:36`)
    → อ่าน `/dev/urandom` (Linux) หรือ `openssl_random_pseudo_bytes` ถ้ามี

20. **ไม่มีกฎรหัสผ่าน และผู้ดูแลรีเซ็ตรหัสของผู้ดูแลอีกคนได้** — `backend/user.php:344-400, 587-653`
    → ขั้นต่ำ 8 ตัว และเฉพาะ super_admin รีเซ็ตรหัส admin ได้

## ต่ำ

21. ไม่มีบันทึกการแก้ไขผู้ใช้/สิทธิ์/ค่าตั้งระบบ (มีแค่ `updated_by`) — ตาราง audit log กลาง
22. ส่งเมลไม่สำเร็จลองซ้ำ 3 ครั้งติดกันภายใน ~30 วินาที (`backend/mailer.php:438, 550`) — เพิ่ม `next_try_at` ที่ห่างขึ้นเรื่อย ๆ
23. รายงานที่ยังไม่มี: ของค้างนาน/เคลื่อนไหวช้า, ส่วนต่างการตรวจนับ, สรุปตามพนักงาน (ฝั่งสวัสดิการมีอยู่แล้ว)
24. ฟอร์มล็อกอินไม่มี CSRF token, ออกจากระบบด้วย GET, CSRF token ใช้ `md5(uniqid(mt_rand()))`
25. ล็อกอินตัดช่องว่างหัวท้ายของรหัสผ่าน แต่ตอนเปลี่ยนรหัสไม่ตัด (`config_ctrl/checkmember.php:21`) — ทำให้ตรงกัน
26. `t.js` ที่ราก repo เป็นสคริปต์ทดลองของ Node — ลบ
27. โฟลเดอร์รูปที่อัปโหลด (`assets/img/product`, `assets/img/company`) ไม่มี `.htaccess` ปิดการรัน PHP (ชื่อไฟล์สร้างฝั่งเซิร์ฟเวอร์และตรวจด้วย `getimagesize` อยู่แล้ว — เป็นเกราะสำรอง)
28. `config_ctrl/checksession.php:98` เขียน `http://` ตายตัว

## ไม่พบปัญหา

- SQL injection ในโค้ดหลัก (ค่าที่ต่อสตริงทุกตัวถูก cast เป็น int)
- CSRF ของ api/ — ทุก action ที่เขียนข้อมูลตรวจครบ, ทุก endpoint รับเฉพาะ POST
- XSS — หน้าเว็บและ JS escape ก่อนแสดง (ไม่ได้ไล่ทุกบรรทัดของ `doc-list.js`, `doc-transfer.js`, `product-dept.js`)
- `session_regenerate_id` หลังล็อกอิน, หน้าเว็บหมดเวลาเมื่อว่าง 1 ชั่วโมง
- ลิงก์อนุมัติ/เซ็นรับ: มีวันหมดอายุ, ลิงก์อนุมัติใช้ครั้งเดียวและผูกกับคน
- ทุกการเปลี่ยนยอดสต็อกลง `tb_stock_movement` พร้อม `balance_after` และล็อกแถว
- `main.php?page=` ใช้รายการที่อนุญาต ไม่ include ไฟล์ตามค่าที่ส่งมา
- ระบบสวัสดิการล่ม ไม่กระทบสต็อก (สต็อกไม่เคยเรียกออกไปหา)
- ไม่มี TODO/FIXME ค้างในโค้ด
